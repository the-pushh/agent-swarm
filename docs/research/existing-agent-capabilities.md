## Material gaps for a cross-app personal assistant

1. **Persistent goals and follow-through.** Chat messages and numbered review aliases live in the `ChatSession`/`AgentTools` objects; there is no persisted cross-app task or obligation lifecycle in those implementations. Domain proposals persist separately. A workflow such as “track this promise until it is done” needs a new durable task record with source links, status and next check. [Session](../../agents/chat/agent.py), [tool state](../../agents/chat/tool_implementations.py).
2. **Full communication context.** Gmail reads one message body; attachments are marked unread/incomplete. Thread metadata is checked before writing, but the model does not receive a full thread history through the current read operation. Name-to-contact resolution is also not an exposed tool. [Gmail reads](../../providers/gmail.py), [allowlist](../../agents/chat/tools.py).
3. **Additional apps and research.** The model allowlist covers Gmail and Calendar only. It does not expose documents, notes, team chat, browser research or screen-memory retrieval. These require explicit adapters and data contracts. [Allowlist](../../agents/chat/tools.py).
4. **Always-on triggers and delivery.** Monitoring stops with the TUI, and chat shares one worker with calendar monitoring. There is no OS notification integration in the documented calendar workflow. A durable scheduler and delivery channel are separate work. [Worker/scheduler](../../tui/__main__.py), [calendar limitations](../calendar-setup.md).
5. **Richer review UX.** The current delivery surface is a terminal with slash commands. Chat draft revisions exist, but review/execution use separate literal commands. A visual action queue with source evidence, editable fields and clear stale/failed statuses is an interface project over existing operations. [Chat UI](../../tui/chat.py), [chat commands](../../agents/chat/agent.py).
6. **Complete mailbox search and coverage.** Chat searches saved assessed results; scans advance one page at a time. It cannot truthfully claim to have searched an entire inbox from one scan. A source-side search tool and explicit coverage are needed for historical recall. [Chat email list](../../agents/chat/tool_implementations.py), [scan](../../agents/email/control_loop.py), [inbox listing](../../providers/gmail.py).
7. **Product-grade multi-user operation.** Current storage uses local files and process locks; approval is trusted local-interface state. Hosted tenancy, authenticated review, service-level job ownership and cross-device identity are not provided by these modules. [Email storage](../../agents/email/agent.py), [Calendar storage](../../agents/calendar/agent.py), [chat review](../../agents/chat/tool_implementations.py).

These are inventory conclusions from the inspected interfaces and storage, not claims that any unseen demo has solved these problems.

## Reuse recommendation

Build the first pilot around one linked workflow: **an email needing a commitment → a suggested reply plus feasible calendar block → exact human review → saved draft/event → tracked follow-up**. The existing implementation supplies triage, drafting, availability, proposals and guarded external writes. The durable commitment/follow-up record and its cross-app evidence links are new work. The final step should be described as planned until implemented.

Retain the provider contracts, deterministic calendar calculations, proposal fingerprints and account boundaries. First separate the chat dispatcher from its direct dependence on TUI tab adapters so another UI can call domain operations cleanly. That coupling is visible in calls such as `tab.run`, `tab.refresh`, `tab.details` and `tab.open` inside [AgentTools](../../agents/chat/tool_implementations.py). This is an architectural recommendation, not an existing feature.

Do not spend the first iteration on recursive delegation or arbitrary app control: the implemented coordinator already sequences narrow domain tools. Invest in a complete user-visible workflow and measure its reliability before adding agent count.
